# 우타링 (Utaring)

> 앱 이름은 **우타링**입니다. 歌(우타, 노래)에 -ring을 붙인 것으로, 한국어 화자가 한눈에
> 읽히고 무엇을 하는 앱인지 소리로 전합니다. 저장소 이름 `Just`와 번들 ID
> `com.coby.just`는 그대로 둡니다 — 바꾸면 기기의 앱 데이터와 프로비저닝이 함께 끊깁니다.

좋아하는 일본 아이돌 — KAWAII LAB. 다섯 그룹, iLiFE!, =LOVE — 의 노래 가사로 일본어를 공부하는 iPhone / iPad 앱.

노래 한 곡이 학습 한 세트입니다. 가사 줄을 누르면 그 줄이 단어로 쪼개지고, 담은
단어는 실제로 나온 가사를 예문 삼아 간격 반복 복습으로 넘어갑니다.

## 만드는 법

```bash
tuist install    # Swift 패키지(Google Mobile Ads) 받기
tuist generate
```

Xcode 26.6 이상(27 포함), iOS 26 SDK, Swift 6.3 기준입니다.

## 실행 전 준비

계정이 없습니다. 권한 요청은 **복습 알림을 켤 때의 알림 권한**과 **가사 카드를
사진 앱에 저장할 때의 사진 추가 권한**뿐이고, 둘 다 그 기능을 쓸 때에만 묻습니다. 광고 동의가 필요한 지역(EEA·영국)에서는 첫 실행 때 Google의
광고 동의 화면이 뜹니다. 곡 정보는 Apple의 공개 iTunes 검색 API에서, 영상은
YouTube에서 오므로 시뮬레이터에서도 그대로 동작합니다.

하나만 준비하면 됩니다 — 곡의 영상을 찾는 **YouTube Data API 키**입니다.
[Google Cloud Console](https://console.cloud.google.com/apis/credentials)에서
YouTube Data API v3를 켜고 API 키를 만든 뒤, 프로젝트를 생성할 때 환경 변수로
넘깁니다.

```bash
TUIST_YOUTUBE_API_KEY=여기에_키 tuist generate --no-open
```

매번 적기 싫으면 저장소 루트의 `.env`에 둡니다. `.mise.toml`이 이 파일을 읽으므로
mise가 활성화된 셸(`mise activate`)에서는 `tuist generate`와 `Scripts/setup.sh`가
그대로 받습니다. `.env`는 커밋되지 않습니다.

```bash
# .env
TUIST_YOUTUBE_API_KEY=여기에_키
# 출시 빌드에서만 필요합니다. 없으면 Google 테스트 ID가 들어갑니다.
TUIST_ADMOB_APP_ID=ca-app-pub-XXXXXXXXXXXXXXXX~XXXXXXXXXX
TUIST_ADMOB_INTERSTITIAL_ID=ca-app-pub-XXXXXXXXXXXXXXXX/XXXXXXXXXX
```

`.env`가 없을 때의 동작은 mise 버전에 따라 다를 수 있으니, 키가 없어도 빈 파일
하나는 만들어 두는 편이 안전합니다(`touch .env`). CI도 그렇게 합니다.

키 없이 생성하면 앱은 그대로 돌지만 영상을 찾을 수 없어 **모든 곡을 30초
미리듣기로** 재생합니다.

**할당량은 기기마다가 아니라 API 키 하나에 걸립니다.** 출시 빌드에는 키가 하나
박혀 나가므로, 앱을 설치한 모든 사람이 하루 10,000단위를 나눠 씁니다. 검색 한 번이
100단위라 전체 사용자를 합쳐 **하루 검색 약 100회**입니다(채널 업로드 목록은
50개에 1단위라 훨씬 쌉니다). 한 번 찾은 영상은 기기에 남아 다시 묻지 않지만,
사용자가 늘면 할당량이 먼저 바닥납니다 — 바닥나면 그날 남은 시간 동안 새 곡은
30초 미리듣기로 재생됩니다.

앱에 들어간 키는 앱 바이너리에서 꺼낼 수 있으므로, Cloud Console에서 반드시
제한을 걸어 둡니다.

- **API 제한**: YouTube Data API v3만 허용
- **애플리케이션 제한**: iOS 앱, 번들 ID `com.coby.just`
  (iOS 제한은 요청 헤더로 판별하는 것이라 완전한 방어는 아닙니다)
- **할당량 알림**: Cloud Monitoring에서 일일 사용량 경보를 걸어 두기

근본적인 해결은 키를 서버에 두고 검색 결과를 캐시해 모든 사용자가 나눠 쓰는
프록시입니다. 아직 없고, 남은 일로 둡니다.

표기가 그룹 이름(또는 4자 이상의 별칭)을 포함하면 그 그룹의 곡으로 봅니다 —
「=LOVE & ≠ME」, 「モーニング娘。'17」, 「椎名林檎と新しい学校のリーダーズ」도 제 그룹을
찾습니다.

그룹을 고를 때 가사 확보율을 함께 봤습니다(2026-09 표본: 그룹당 10곡을 LRCLIB에서
찾음). ≒JOY·AKB48 9/10, 乃木坂46·≠ME·NMB48·NiziU 7/10처럼 높은 그룹이 있고, 신생
그룹과 Hello! Project는 낮습니다 — 이런 곡은 가사 붙여넣기로 공부합니다.

그룹이 서른 개를 넘으면서 첫 실행에 그룹 사진을 받을 때 조회 서비스의 분당 한도(약
20회)에 걸립니다. 거절된 그룹은 35초 뒤에 다시 묻고(최대 세 번), 받은 페이지는
기기에 남아 다음 실행부터는 바로 뜹니다.

곡 목록은 iTunes 조회(`lookup?id=…&entity=song`)에서 옵니다 — 새 싱글이 나오면 앱
업데이트 없이 뜹니다. 이름이 아니라 ID로 찾는 이유는 동명이인입니다. 조회는 모든
녹음을 돌려주므로 Instrumental·off vocal은 빼고, 같은 곡의 여러 판은 하나로 접어
**새 것부터** 늘어놓습니다.

그룹 카드의 사진은 아티스트의 공개 Apple Music 페이지 `og:image`에서 읽고(조회 API에는
아티스트 사진이 없습니다), 실패하면 가장 새 앨범 커버가 대신 섭니다. 페이지와 사진
주소는 기기에 남겨 다음 실행의 첫 프레임부터 뜹니다(`GroupPageCache`, 하루 지나면
뒤에서 갱신). 사진이 아직 안 왔으면 그룹 색 그라데이션이 카드 자체라 깜빡이지 않습니다.

목록과 그룹 화면은 밝고 화사하게, **플레이어와 가사는 다크를 유지**합니다. 가사는
어두운 배경에서 읽기가 훨씬 편하고, 이 앱에서 가장 긴 시간이 가사를 읽는 시간입니다.

두 톤은 **팔레트 하나가 색상 모드를 따라 바뀌는** 것으로 구현됩니다.
`JustTheme.Ink`와 `Surface`가 다크·라이트 값을 각각 갖고 그리는 자리에서 해석되므로,
목록 화면은 루트에 `.environment(\.colorScheme, .light)` 한 줄을 붙이는 것으로
뒤집히고 그 안의 모든 라벨이 따라옵니다. 화면마다 수십 개의 색 참조를 고치는
대신 한 곳을 고쳤습니다.

앱 아이콘은 하트 안의 「歌」에 반짝임 셋입니다(`Scripts/make-icon.py`). 한자만으로는
일본어를 말하고 아이돌을 말하지 못했고, 하트만으로는 그 반대였습니다. 말풍선 꼬리도
시도했다가 뺐습니다 — 하트는 이미 뾰족한 끝이 있어서 꼬리를 붙이면 끝이 둘이 되고,
작은 크기에서 렌더링 오류처럼 읽혔습니다.

### 가사 싱크

두 가지가 어긋날 수 있고 원인이 다릅니다.

**미리듣기에서는 가사가 따라가지 않습니다.** 영상을 찾지 못한 곡은 30초 클립이고,
그 클립은 곡 중간에서 잘려 나옵니다(미리듣기 첫 1초의 평균 음량이 클립 전체
평균과 0.3~3.5dB 차이뿐 - 곡의 시작이라면 무음에서 출발합니다). Apple은 어디서
잘랐는지 공개하지 않으므로 클립 시간을 곡 시간으로 환산할 방법이 없습니다.
그래서 환산하지 않고, 강조·자동 스크롤·줄 탭 이동·구간 반복을 모두 멈추고 이유를
한 줄로 표시합니다. 가사는 그대로 읽고 눌러 뜻을 볼 수 있습니다.

**전곡 재생에서 몇 초 어긋나는 것은 시트가 그렇게 적힌 것입니다.** 시트를 만든
사람이 한 줄의 시작을 어디로 잡았는지(첫 박, 첫 음절, 그 앞의 숨)는 데이터에
없고, 대조할 두 번째 출처도 없어서 자동으로는 찾을 수 없습니다. 대신 곡별로
`StudySong.lyricsOffset`에 저장되는 보정값을 사용자가 정합니다 - 다이얼로
0.1/0.5초씩 밀거나, **지금 들리는 줄을 눌러** 한 번에 맞춥니다. 앱이 짚고 있는
줄이 아니라 실제로 들리는 줄을 눌러야 합니다(짚고 있는 줄은 정의상 틀린 줄입니다).
±5초를 넘기면 받지 않습니다 - 그건 타이밍이 아니라 다른 편집본이라는 뜻입니다.

### 광고

광고는 하나뿐입니다 — **곡을 분석하며 기다리는 동안 전면 광고 한 번**. 가사가 아직
준비되지 않았고 무엇을 해도 대기가 줄지 않는, 화면을 쓰지 않는 유일한 순간입니다.

목록 아래에 붙어 있던 배너들은 걷어냈습니다. 마지막 행 밑의 띠는 모든 화면 끝의
잡동사니로 읽혔고, 벌이도 적었습니다.

띄우지 않는 곳도 적어 둡니다. **가사와 플레이어** 위, **문제가 떠 있는 화면**,
그리고 **빠른 번역 / AI 번역을 고르는 질문** 위 — 그건 독자가 답하는 중인
질문입니다. 그래서 선택이 끝나고 분석이 실제로 시작된 뒤에만, 남은 줄이 5줄 이상일
때만 띄웁니다. 더 적으면 광고가 닫히기 전에 분석이 끝납니다.

**곡당 한 번**, 그리고 **2분 안에 두 번은 없습니다.** 그룹의 곡을 넘겨 보는 독자가
매 곡 광고를 보는 일은 없어야 합니다.

**광고가 곧 기다림입니다.** 해석은 광고 뒤에서 계속 돌고(측정: 빠른 해석 68줄이 광고가
떠 있는 동안 끝남), 광고를 닫으면 남은 줄을 기다리지 않고 곧바로 곡이 열립니다 — 남은
줄은 「지금 듣기」와 같은 방식으로 가사 뒤에서 채워집니다. 광고를 본 뒤 진행 막대를 또
보게 하면 "광고가 끝나야 해석이 시작된다"로 읽혔습니다. 광고는 앱을 켤 때 미리 받아 두어,
해석이 시작되는 순간 바로 뜹니다. 곡의 영상 찾기도 곡을 여는 순간 가사·해석과 **동시에**
시작하므로, 광고가 닫힐 때쯤이면 영상도 준비되어 있습니다.

`GADApplicationIdentifier`와 전면 광고 단위 ID(`AdMobInterstitialUnitID`)는
`tuist generate` 때 환경 변수 `TUIST_ADMOB_APP_ID` / `TUIST_ADMOB_INTERSTITIAL_ID`에서
Info.plist로 들어갑니다. 비워 두면 **Google 공개 테스트 값**이 들어가고, Debug
빌드는 앱 ID와 상관없이 항상 테스트 광고 단위를 씁니다 — 개발 중에 실제 광고를
띄우거나 누르는 일이 없도록. `fastlane beta`는 두 값이 비었거나 테스트 값이면
빌드를 거부합니다.

광고는 **Google UMP(User Messaging Platform) 동의 흐름을 거친 뒤에만** 요청합니다.
앱을 켜면 동의 정보를 갱신하고, 필요한 지역이면 Google의 동의 화면을 띄우고,
`canRequestAds`가 참일 때에만 SDK를 시작하고 광고를 불러옵니다(`AdsConsent`).
EEA·영국 사용자는 나중에 답을 바꿀 수 있어야 하므로, 설정 화면에
`AdsConsent.shared.isPrivacyOptionsRequired`일 때 `presentPrivacyOptions()`를 부르는
행을 두어야 합니다.

모든 요청은 **비맞춤 광고**(`npa=1`)로 보냅니다. 맞춤 광고는 쓰지 않으므로 App
Tracking Transparency 프롬프트도 띄우지 않습니다. 광고 기여도는 추적 권한이 필요
없는 SKAdNetwork(`SKAdNetworkItems`, Google의 `cstr6suwn9.skadnetwork`)로만
잡힙니다.

**iTunes도 YouTube도 가사를 제공하지 않습니다.** 싱크 가사는 LRCLIB에서 받습니다.

**가사 저작권은 열린 문제입니다.** LRCLIB는 사용자들이 올린 가사를 모은 커뮤니티
데이터베이스이고, 올라온 가사의 이용 허락을 LRCLIB가 받아 둔 것이 아닙니다. 이 앱은
가사를 저장소에 담지 않고 실행 시 받아 기기에만 두지만, 화면에 가사 전문을 표시하는
것은 사실입니다. 출처 표기(LRCLIB)를 화면에 두는지, 권리자 요청 시 내리는 절차를
어떻게 할지는 출시 전에 정해 둘 일입니다 — 스토어 심사나 권리자 신고로 문제가 될 수
있는 부분입니다.

### 가사 찾기

LRCLIB에 처음의 일곱 그룹 곡은 **절반쯤** 있습니다(2026-09 실측: 216곡 중 99곡). 나머지는
아직 아무도 올리지 않은 신곡·수록곡이라, 찾는 방법을 바꿔도 나오지 않습니다. 있는 것을
놓치지 않는 데 집중합니다.

1. 정확 조회(아티스트·제목·앨범·길이) → 구조 검색 → 자유 검색, 표기를 바꾸며 반복합니다.
   카탈로그 표기 그대로, 괄호 꼬리를 뗀 제목, 첫 아티스트만, **부제·판 표기를 뗀 제목**
   (「〜…〜」, 「-TV size-」, 「- Single Version」), 그룹의 **일본어 표기 별칭**
   (`IdolGroup.aliases`: フルーツジッパー, イコラブ …), 마지막으로 **제목만**. 제목만
   찾을 때는 길이 ±10초와 가나 비율이 다른 곡을 걸러 줍니다(실측 +4%).
2. 길이가 맞는 가사가 없고 **다른 판의 일본어 가사**(라이브의 원곡, TV 사이즈의 완곡)만
   있으면 시간을 떼고 글로만 씁니다 — 줄이 어긋나게 따라가는 것보다, 따라가지 않는 편이
   낫고, 없는 것보다는 있는 편이 낫습니다.
3. 그래도 없으면 **직접 붙여넣기**. 가사를 못 찾은 카드에서 가사를 붙여 넣으면 그 가사로
   공부합니다. `[00:12.34]` 시간이 있으면 노래를 따라가고, 글만 있으면 줄을 눌러 공부합니다.

번역본을 원문으로 착각하지 않도록 가나가 있는 줄이 절반을 넘는 가사만 받습니다.

### YouTube 재생

곡은 그룹의 뮤직비디오로 재생됩니다. 계정이 필요 없는 유일한 전곡 경로이고,
가사 싱크가 곡 전체를 따라갑니다.

내장 플레이어의 약관을 지킵니다. **영상은 재생 중 화면에 있어야** 하므로 플레이어를
접으면 영상이 멈추고, 미니플레이어의 재생 버튼은 플레이어를 다시 열어 이어 봅니다.
가사 전체화면에서도 영상은 위에 남습니다. 오디오만 재생하거나 백그라운드로 보내는
일은 없습니다. 플레이어 자체 컨트롤은 꺼 두고 앱의 재생 버튼·슬라이더가 대신합니다
(한 세트면 충분합니다).

영상은 세 단계로 찾습니다.

1. **그룹의 공식 채널.** 명단(`IdolGroup.youtubeChannels`)에 각 그룹의 채널, 뮤직비디오를
   올리는 레이블 채널(KAWAII LAB.), 레이블 음원의 자동 생성 「Topic」 채널을 실어 둡니다.
   곡을 열면 그 채널들의 업로드 목록을 **최근 2000개까지** 받아(50개에 1단위) 제목으로
   맞춥니다. 처음엔 200개만 봤는데, 채널마다 쇼츠·비하인드가 매일 올라와 옛 MV가 밀려
   났습니다(실측: 乃木坂46 40곡 중 11곡 → 1000개로 36곡, AKB48 17 → 37). 목록은 기기에
   남고 **하루 지나면 새로 올라온 페이지만** 받아 앞에 붙이므로(보통 한 번의 요청) 신곡의
   영상이 나오는 주에 들어옵니다.

   제목은 폭(전각·반각)과 장음을 접어서 비교합니다 — 카탈로그는 「LOVEマシ-ン」처럼
   하이픈을, 영상은 「LOVEマシーン」처럼 장음을 씁니다. 판 표기(「 -ZZ ver.-」, 「(2024
   ver.)」)·멤버 크레딧(「/亀井絵里・…」)·「・・・(略)」로 줄인 긴 제목은 떼어낸 핵심
   제목으로도 찾습니다. 일본어는 두 글자(「走れ」)도 제목으로 쓰고, 로마자는 세 글자
   미만을 버립니다.
2. **검색.** 채널에 없는 곡만 `"<아티스트> <곡명> MV"`로 검색합니다(100단위). 분류는
   가리지 않습니다 — 아이돌 MV는 「음악」이 아니라 「엔터테인먼트」로 올라간 것이 많습니다. 결과 중
   **제목에 곡명이 있는 것**에서 MV·Music Video와 그룹 채널·레이블 채널·Topic 채널을

### 로컬 저장

곡을 열면 그 곡에 딸린 모든 데이터가 기기에 남습니다.

| 데이터 | 위치 | 비고 |
|---|---|---|
| 가사 (LRC) | `StudySong.lyricsData` | 오프라인 재열람 가능 |
| 줄별 해석 전체 | `StudySong.analysisData` | 번역 + 단어 + 문법. 모델은 곡당 한 번만 돈다 |
| 난이도 히스토그램 | `StudySong.levelCounts` | 목록에서 해석을 디코드하지 않아도 되도록 비정규화 |
| 단어·복습 일정 | `VocabEntry` / `ReviewState` | |
| 앨범아트 | Caches/Artwork | URL 해시 파일명. 시스템이 회수 가능 |

곡을 처음 열면 **전곡 해석이 자동으로 시작**됩니다. 줄마다 눌러 기다리는 대신
한 번에 만들어 저장합니다. 진행분은 즉시 기록되므로 중간에 닫아도 버려지지 않고,
다시 열면 남은 줄부터 이어서 합니다.

해석을 빠르게 하는 것 세 가지가 들어 있습니다. 후렴처럼 **같은 줄이 반복되면
한 번만 모델에 묻고** 나머지 인덱스에 복사합니다. 모델 세션은 줄마다 새로 만들지
않고 8줄마다 재활용합니다 — 매번 만들면 열다섯 줄짜리 지시문을 그때마다 다시
처리합니다. 저장은 다섯 줄마다 합니다(매 줄 저장은 곡 길이에 대해 제곱으로 늘어남).

곡을 열 때 아직 번역할 줄이 남아 있으면 **「어떻게 번역할까요?」**를 먼저 묻습니다 —
「빠르게」(몇 초, 뜻·문법은 정확, 문장은 직역에 가까움)와 「AI로 정확하게」(앞뒤 줄까지
읽어 자연스럽게, 몇 분) 두 카드에 각각 한 문장 설명이 붙습니다. 설정에 묻힌 선택기는
기다리는 동안 아무도 찾지 않으므로, 답이 필요한 그 순간에 묻습니다. 「다음에도 이걸로
열기」를 켜면 더 묻지 않고, 설정에서 다시 켤 수 있습니다. 이미 다 번역된 곡은 묻지
않습니다 — 답이 바꿀 것이 없습니다.

화면 문구에는 기술 용어를 쓰지 않습니다. 「AI 번역」과 「빠른 번역」, 「간단 번역」이
전부입니다. 줄 카드의 버튼도 「정확하게 다시 번역」입니다.

기다리기 싫으면 **'지금 듣기'**로 바로 넘어갈 수 있고, 남은 줄은 들으면서
이어서 해석합니다. **긴 곡은 알아서 넘어갑니다** — 첫 두 줄을 넘긴 뒤 남은 시간이
30초를 넘으면 플레이어를 먼저 열고 나머지를 뒤에서 채웁니다(`WaitBudget`). 완성된
곡을 보여주는 것이 여전히 기본이고, 빨리 끝나는 곡은 끝까지 기다립니다 — 사람에게
요구할 수 있는 대기와 기기가 할 수 있는 대기는 다르기 때문입니다.

속도를 위해 정확도를 조금 내준 것이 세 가지 있습니다. **문법 노트를 더 이상
묻지 않습니다** — 측정에서 아홉 줄 중 다섯~일곱 줄이 비어 있었는데, 거의 비는
칸도 모델이 매 줄 지나가는 칸입니다. **단어는 한 줄에 최대 세 개**입니다(전에는
여섯). 그리고 **greedy 디코딩**을 씁니다 — 표본 추출 비용이 사라지고, 무엇보다
같은 줄이 같은 답을 주므로 프롬프트를 바꿨을 때 숫자가 움직이면 그것이 이유가
있어 움직인 것입니다(전에는 잡음을 넘겨보려고 세 번씩 돌려야 했습니다).

영어 줄은 번역 한 칸만 묻습니다. 단어와 문법은 어차피 버리므로, 버릴 출력을
생성하느라 기다릴 이유가 없습니다.

자동 해석 시점은 설정에서 고릅니다 — 항상 / **저전력 모드가 아닐 때**(기본) / 안 함.
기본값이 저전력 모드를 따르는 이유는, 사용자가 이미 시스템에 에너지 사용 방침을
말해 두었기 때문입니다. 학습 앱이 그걸 앞질러 판단할 이유가 없습니다.

### 해석이 빠지는 줄을 없애는 세 층

**영어 구절은 번역만 합니다.** J-POP은 후렴이 통째로 영어인 경우가 흔합니다. 그
줄도 노래의 일부라 뜻은 알려주지만, 거기서 외울 일본어 단어는 없습니다 —
`baby`에 가나 읽기를 지어 붙인 카드는 복습 일정에 들어가서 계속 돌아옵니다.
가나나 한자가 하나라도 있으면 일본어로 보고(비율이 아닙니다 — 영어 줄에 섞인
일본어 한 단어도 배울 값이 있습니다), 섞인 줄에서는 일본어 단어만 남깁니다.

**실패한 줄은 진전이 있는 동안 다시 시도합니다.** 남은 줄이 없어질 때까지 돌면
항상 실패하는 줄에서 영원히 돌아오지 않으므로, 조건은 완료가 아니라 진전입니다 —
한 바퀴가 아무것도 해결하지 못하면 끝입니다. 한 줄당 최대 한 바퀴이므로 반드시
끝납니다.

**그래도 남은 줄은 시스템 번역으로 채웁니다.** Apple Intelligence는 최신 기기를
요구하지만 Apple 번역은 그렇지 않습니다. 예전 기기에서는 해석이 사전 뜻에서
멈추고 번역이 아예 없었는데, 그게 정작 필요한 절반입니다. 뉘앙스는 없는
직역이지만 번역은 번역입니다.

### 해석 방식은 두 가지고, 고를 수 있습니다

같은 세 가지 질문 — 단어가 무슨 뜻인지, 어떤 문법을 쓰는지, 줄이 무슨 말인지 —
에 서로 다른 것이 답합니다.

| | 빠르게 | 정확하게 |
|---|---|---|
| 단어 | 번들 사전 | 모델 + 사전이 사실 교정 |
| 문법 | 패턴 매칭 | 패턴 매칭 |
| 문장 | 시스템 번역(직역) | 모델이 앞뒤 줄까지 읽고 해석 |
| 한 곡 | 몇 초 | 몇 분 |

원래는 선택이 아니라 기기 사양이었습니다. Apple Intelligence가 없으면 사전으로
떨어지고, 있으면 거절할 방법이 없었습니다. 하지만 그 폴백은 구형 기기만을 위한
것이 아닙니다 — 후렴을 **지금** 보고 싶은 사람, 배터리가 아까운 사람, 이미 한 번
읽은 곡을 다시 여는 사람에게 느린 쪽은 선택하지 않은 비용입니다. 그래서 폴백이
모드가 되고, 모드가 설정이 되었습니다.

**대기 화면에도 전환 버튼이 있습니다.** 조급함은 설정 화면이 아니라 기다리는
자리에서 생기고, 거기서 찾을 수 없는 모드는 없는 모드입니다. 누르면 진행 중인
줄만 모델이 끝내고 나머지는 즉시 채워집니다. 이미 해석된 줄은 좋은 답을 그대로
유지합니다.

빠르게로 해석한 곡을 정확하게로 바꾸면 **다시 해석합니다.** 사전 결과도 번역을
갖고 있어서, 번역이 있으면 완료라는 기존 규칙만으로는 빠르게 읽은 곡이 영원히
빠른 상태로 남았습니다. 반대 방향은 대칭이 아닙니다 — 빠르려고 이미 받은 더 좋은
답을 버릴 이유는 없습니다.

### 문법은 물어보지 않고 찾습니다

모델에 문법 노트를 요청하는 것은 그만뒀습니다. 아홉 줄 중 다섯~일곱 줄이 빈
배열로 돌아왔고, 쓰이지 않는 필드도 생성되는 출력만큼 비용을 냅니다. 그런데 그걸
끊으면 문법 모아보기 화면에 공급이 사라집니다.

그래서 찾습니다. 일본어 문법 패턴은 유한하고 잘 정리된 집합이고, 어떤 줄이
「〜てしまう」를 포함하는지 아닌지는 판단이 아니라 사실이며, 그게 무슨 뜻인지는
곡에 따라 달라지지 않습니다. 이 파일의 나머지가 이미 하는 분업과 같습니다 —
판단은 모델, 사실은 고정 데이터.

줄에 맞춘 설명을 포기하는 대신, 항상 작동하고 항상 같은 말을 하고 생성 비용이
0입니다. 긴 패턴은 자기가 포함한 짧은 패턴을 가립니다 — 「なきゃ」는 「ない」에
대한 수업이 아닙니다. 한 줄에 최대 3개인데, 짧은 가사 한 줄에 노트 여덟 개는
수업이 아니라 소음입니다.

모델이 있는 기기에서는 **모델이 먼저 다 시도한 뒤에** 남은 줄만 채웁니다. 그러지
않으면 위의 재시도가 무의미해지고 일시적 실패가 직역으로 굳습니다.

`Translation` 프레임워크는 뷰 밖에서 `init(installedSource:target:)`만 쓸 수
있어서, 언어팩 다운로드는 설정 화면의 버튼(`.translationTask`)에서 시작합니다 —
시스템 프롬프트가 뜨는 일이라 해석 도중이 아니라 사용자가 연 화면에 있어야
맞습니다. 스위치로 끌 수 있고 기본은 켬입니다.

### 해석 품질 측정

`Report/SenseiReport.swift`는 테스트가 아니라 **측정 장치**입니다. 고정된 가사에
실제 해석기를 돌려 나온 것을 찍고, 셀 수 있는 실패(이웃 줄 침범, 금지어,
번역에 남은 일본어, 부풀림, 사전으로 대체된 줄)와 소요 시간을 표로 냅니다.
품질은 단언할 수 없지만 이 숫자들은 단언할 수 있고, 두 실행을 비교하는 것이
프롬프트나 묶음 변경을 판단하는 유일한 방법입니다.

**별도 타깃(`JustReport`)이고 앱이 호스트입니다.** 그래서 실기기에서 돌릴 수
있습니다 — 시뮬레이터의 온디바이스 모델 자산은 하루에 세 번 사라졌고, 그때마다
보고서는 「모든 줄이 사전으로 대체됐습니다」라고 스스로 말합니다.

```bash
# 시뮬레이터
xcodebuild -workspace Just.xcworkspace -scheme JustReport \
  -destination 'platform=iOS Simulator,name=iPhone 17' test

# 실기기 (모델이 진짜인 곳). 기기 잠금을 풀어야 합니다.
xcodebuild -workspace Just.xcworkspace -scheme JustReport \
  -destination 'platform=iOS,name=Coby' -allowProvisioningUpdates test
```

기본 `Just` 스킴의 테스트는 `JustTests`만 돌립니다. 유닛 테스트는 1초 미만이고
매 변경마다 돌리는 것이라, 그 앞에 앱 실행을 얹지 않기 위해 타깃을 나눴습니다.

### 오매칭을 재는 눈

커버리지 보고서에 **「가나 표기가 한자 표제어로 잡힌 것」**을 셉니다. 가사가 가나로
쓴 말이 한자 단어로 돌아온 경우인데, 옳을 때도(ゆめ → 夢) 있고 그 반대가 문제였습니다
— 부정 어미 「ない」가 **119줄**에서 「泣く(울다)」로, 「また」가 「待つ」로, 「いい」가
「言う」로 잡혔습니다. 가나 단어를 활용 되돌리기로 **다른 가나로 구부린 뒤** 읽기
인덱스에서 한자 동사를 찍어 온 것입니다.

세 가지로 막았습니다. 읽기 인덱스는 **먼저 들어온 항목** 대신 **흔한 뜻**(손으로
확인한 것, 그중 쉬운 급)을 고릅니다. 가나로 쓴 말은 같은 가나 표제어가 있으면 그것을,
없으면 손으로 확인한 흔한 한자 단어까지만 받고 수입된 희귀 표기로는 넘어가지
않습니다. 그리고 되돌린 후보 중 **어미(た·て·ない·ます·よう)가 붙어 있던 것만**
읽기로 한자 동사에 닿을 수 있고, 끝 글자 하나를 바꿔 만든 후보는 표기로만 찾습니다 —
어미는 동사가 있었다는 증거고, 끝 글자는 증거가 아닙니다.

측정: 오매칭 **227 → 25**, 남은 25건은 전부 옳은 매칭입니다. 커버리지는 66% → 63%로
내려갔는데, 빠진 3점이 가짜 적중이었습니다.

### 번들 사전

`Modules/JustSensei/Resources/seed-dictionary.json`은 생성물입니다.

```bash
python3 Scripts/build-dictionary.py
```

층을 순서대로 쌓아 만듭니다 — 뒤 층이 앞 층을 덮지 않습니다.

- `Scripts/curated.json` — 손으로 확인한 항목. 품사·JLPT 등급까지 신뢰합니다.
- **가져온 뜻·읽기** — 옆 프로젝트 `jlpt-app`의 일한 단어 데이터(~6.8천). 원본의
  `lv`는 난이도가 아니라 교재 소속 태그라(전 행이 `n1`) 버립니다. 옆 프로젝트가
  없으면 직전 빌드의 항목을 그대로 유지합니다.
- `Scripts/corrections.json` — 가져온 뜻·읽기의 수정. JMdict 영어 뜻과 대조해
  한자어 거짓짝(配信이 「배신」), 다른 읽기의 뜻(角 かく에 「뿔」), 읽기 오타를
  고칩니다.
- `Scripts/additions/*.json` — 새 단어. 사전에 없던 JLPT 단어와, 어느 목록에도
  없지만 아이돌 가사가 기대는 어휘(외래어·의성의태어·팬 용어).
- `Scripts/data/jlpt-levels.tsv` — JLPT 등급. 등급이 없는 행에 채웁니다.
- `Scripts/data/jmdict-pos.tsv` — JMdict 품사. 품사가 없는 행에 채웁니다.
  `Scripts/extract-jmdict.py`로 다시 뽑습니다(JMdict 원본 필요, 저장소엔 없음).

결과가 이전보다 10% 넘게 줄면 **쓰기를 거부**합니다 — 옆 프로젝트가 사라진 채
빌드하면 어휘 대부분을 잃기 때문입니다. 지금은 약 12,000단어이고, 그중 등급이
붙은 것이 약 7,900개, 품사가 붙은 것이 약 11,600개입니다.

### 해석 파이프라인

```
가사 한 줄
 ├─ CFStringTokenizer   문맥 인식 분절 + 읽기
 ├─ NLTagger            사전형(lemma) · 품사
 ├─ FoundationModels    한국어 번역 · 뜻 · 뉘앙스 (guided generation)
 └─ 번들 사전 교차검증   표제어 · 읽기 · 품사 · JLPT 등급 덮어쓰기
                        (가사에 쓰인 표기를 읽기보다 우선)
```

프롬프트에는 **그 줄 단어의 사전 뜻**이 함께 들어갑니다(`<words>`). 모델은 문장을
읽는 데는 강하고 단어를 기억하는 데는 약해서, `空`을 「공기」(空気)로 옮기는 일이
반복됐습니다 — 사전은 「하늘」로 정확히 갖고 있는데 아무도 모델에게 말해주지
않았습니다. 넣는 개수는 네 개로 제한합니다. 문맥 창이 세 줄에서 넘치는 상황에서
줄 길이에 따라 늘어나는 목록은 그 시점을 앞당깁니다.

번역으로 받아들이는 조건도 기계적으로 검사합니다. **한글이 인용부호 밖 글자의
다수**여야 하고, 인용부호 밖에 일본어가 남아 있으면 받지 않습니다. 인용은
괜찮습니다 — 원문이 「さよなら」를 인용하면 번역이 그대로 인용하는 것이 옳고,
영어 후렴을 인용하는 한국어 문장도 옳습니다. 「한글이 하나라도 있으면」으로
두었을 때 「가 fence across from each other.」가 통과했습니다.

온디바이스 모델은 문맥에는 강하고 암기에는 약합니다. 「〜てる」를 「〜ている」로
되돌리거나 가사를 자연스러운 한국어로 옮기는 일은 잘 하지만, JLPT 등급을 지어내고
표제어 자리에 읽기를 쓰기도 합니다. 그래서 **판단은 모델에, 사실은 사전에** 맡기고,
가사에 실제로 없는 단어는 버립니다 (`JustSensei/Sensei.swift`의 `refine`).

## 디자인

밝은 화면(그룹·목록·단어장·연습)은 아이돌 굿즈처럼 꾸밉니다 — 흰 테두리에
인쇄된 핑크 그림자를 단 스티커 카드, 도트 무늬와 반짝이 배경, 마스킹 테이프를
붙인 안내 메모, 누르면 쑥 들어가는 캔디 버튼, 형광펜 밑줄의 섹션 제목, 줄무늬
캔디 진행 바. 전부 `JustDesign`의 공용 부품(`Kitsch.swift`, `JustTheme`)에
있어서 화면 코드는 `justCard()`·`justSurface()`·`.justPrimary`만 씁니다.

어두운 플레이어는 무대라서 담백하게 둡니다. 가사를 읽는 곳이라 무늬나 반짝이를
깔지 않고, 지금 부르는 줄에만 펜라이트 같은 핑크 빛을 줍니다. 장식은
VoiceOver에서 숨기고, 동작 줄이기가 켜져 있으면 반짝이도 멈춥니다.

### 움직임

스티커 콘셉트 하나로 움직임도 맞춥니다(`KitschMotion.swift`). 화면마다 제각각
튀지 않고, 손가락에 같은 방식으로 답하게 하려는 것입니다.

- **누르기** — 스티커 카드(`.buttonStyle(.kitschPress)`)는 누르는 동안 자기 그림자
  위로 눌려 내려앉고, 떼면 살짝 튕기며 올라옵니다. 그림자는 제자리에 두고 카드만
  움직여야 "줄어든다"가 아니라 "눌렸다"로 읽힙니다. 가벼운 햅틱이 함께 옵니다.
- **등장** — 목록과 그리드는 스티커를 한 장씩 붙이듯 조금씩 비뚤게 튀어 들어옵니다
  (`kitschEntrance`). 첫 화면분 12장까지만 순서대로, 그 아래는 기다리지 않습니다.
- **홀로 반짝임** — 그룹 카드는 트레이딩 카드 호일처럼 몇 초마다 빛 띠가 지나갑니다
  (`holoSheen`). 카드마다 차례를 두어 한꺼번에 번쩍이지 않습니다.
- **반짝이 터짐** — 단어를 담을 때, 퀴즈를 맞힐 때, 퀴즈·복습을 끝낼 때 하트와 별이
  튀어나와 떨어집니다(`sparkleBurst`). 끝낼 때는 두 번.
- **흔들림** — 틀리거나 거의 맞힌 답은 고개를 젓듯 좌우로 흔들립니다(`kitschShake`).
- **복습 카드** — 뜻을 확인하면 플래시카드처럼 뒤집히고, 등급을 매기면 왼쪽으로
  튕겨 나가며 다음 카드가 아래에서 붙습니다(`stickerFlick`).
- **가사** — 강조 막대가 줄마다 켜졌다 꺼지지 않고 다음 줄로 미끄러져 내려갑니다.
  이미 부른 줄은 한 단계 더 흐립니다. 반복 중 표시는 숨 쉬듯 깜빡입니다.
- **기다림** — 가사를 찾는 동안 음표 세 개가 차례로 튀고(`BouncingNotes`), 해석 진행은
  줄무늬가 흐르는 캔디 막대입니다. 숫자는 굴러서 바뀝니다.
- **실행 화면** — 홈의 크림 분홍에 아이콘을 올려, 분홍 앱이 검은 화면에서 시작하지
  않게 합니다.

동작 줄이기가 켜져 있으면 전부 멈추거나 투명도 변화만 남습니다. 가사 글자에는
어떤 효과도 겹치지 않습니다.

## 접근성

모든 본문 텍스트가 Dynamic Type을 따르고, 설정을 바꾸면 앱을 다시 열지 않아도
바로 반영됩니다. `Font.system(size:)`는 시스템 글자 크기 설정을 무시하고
`Font.custom(_:size:relativeTo:)`는 폰트 파일 이름을 요구하므로, 글꼴 토큰은
`Font` 값이 아니라 `JustFontStyle`(크기·굵기·기준 텍스트 스타일)이라는 설명이고,
`.font(_:)`가 그리는 자리에서 `@ScaledMetric`으로 크기를 정합니다. 디자인된
포인트 크기를 유지하면서, 실행 중의 설정 변경과 상위 뷰의 `.dynamicTypeSize`
제한까지 따릅니다. 후리가나 자리의 높이도 같은 방식으로 함께 커집니다.

고정 크기로 남긴 것은 SF Symbol 아이콘과 연속일수 링의 숫자뿐입니다. 둘 다
글자와 함께 커지면 안 되는 고정 지오메트리 안에 있습니다.

가사는 여기에 앱 자체의 4단계 조절이 곱해집니다. 시스템 설정과 앱 설정이
같은 텍스트에 함께 작용하므로, 접근성 크기에서는 가사 크기를 낮춰 쓰면 됩니다.

## 딥링크

`just://review`와 `just://words`로 화면을 지정할 수 있습니다. 복습 알림과 위젯이
이 링크를 씁니다 — 알림이 앱을 열되 사용자가 마지막에 보던 화면으로 데려가면
그 알림은 실패한 것입니다.

알림은 `onOpenURL`로 오지 않으므로 `NotificationRouter`가 대신 받습니다. 앱
시작 시점에 등록하는 이유는, 콜드 스타트에서 탭한 알림이 뷰가 만들어지기 전에
전달되기 때문입니다.

## 위젯

홈 화면 위젯은 앱의 SwiftData를 열지 않습니다. 앱이 App Group 컨테이너에
작은 스냅샷(JSON)을 쓰고 위젯은 그걸 읽습니다 — 위젯이 앱 데이터베이스를
여는 것은 스키마 변경을 따라다녀야 하고 쓰기도 못 하며, 숫자 세 개를 읽자고
기존 사용자 데이터를 마이그레이션할 이유도 없습니다.

App Group `group.com.coby.just`가 필요합니다. 자동 서명이 등록하지 못하면
developer.apple.com > Identifiers > App Groups에서 만들고, App ID의
App Groups 기능에서 연결해 주세요.

## 빌드와 배포

옆 프로젝트 `mana`와 같은 구성입니다.

```bash
bash Scripts/setup.sh        # tuist install + tuist generate
bundle exec fastlane test    # 시뮬레이터 테스트
bundle exec fastlane beta    # TestFlight 업로드
```

Tuist 버전은 `.mise.toml`에 고정합니다. 서명은 자동이고 팀 id는 매니페스트에
있으므로 `tuist generate`만으로 기기 빌드가 됩니다.

TestFlight는 App Store Connect API 키로 클라우드 서명합니다 — 인증서를 손으로
갱신할 일이 없습니다. 인증 플래그는 `xcargs` 한 곳에만 둡니다(gym이 archive와
export 양쪽에 그대로 넘기므로 `export_xcargs`로 중복하면 xcodebuild가 거부합니다).

`v*` 태그를 밀면 `.github/workflows/deploy.yml`이 돕니다. 먼저 `test.yml`의 테스트를
돌리고, 통과해야 업로드합니다. 필요한 GitHub 시크릿은 다음과 같습니다.

| 시크릿 | 쓰이는 곳 |
|---|---|
| `APPSTORE_KEY_ID` / `APPSTORE_ISSUER_ID` / `APPSTORE_PRIVATE_KEY` | App Store Connect API 키 (서명·업로드) |
| `YOUTUBE_API_KEY` | `TUIST_YOUTUBE_API_KEY` — 없으면 모든 곡이 미리듣기 |
| `ADMOB_APP_ID` | `TUIST_ADMOB_APP_ID` → `GADApplicationIdentifier` |
| `ADMOB_INTERSTITIAL_ID` | `TUIST_ADMOB_INTERSTITIAL_ID` → `AdMobInterstitialUnitID` |

`fastlane beta`는 YouTube 키와 AdMob ID 둘 중 하나라도 비었거나 Google 테스트 ID면
빌드 전에 멈춥니다. 빠진 채로 올라가면 빌드는 성공하고 앱만 조용히 망가지기
때문입니다.

버전은 `MARKETING_VERSION`과 `CURRENT_PROJECT_VERSION`이 정합니다. Info.plist에
값을 박아두면 fastlane이 넘기는 빌드 번호가 무시되어 업로드가 매번 충돌합니다.

- **마케팅 버전**: `TUIST_MARKETING_VERSION` 환경 변수에서 오고, 없으면 `1.0.0`입니다.
  태그 배포는 태그에서 가져옵니다(`v1.2.0` → `1.2.0`). 수동 실행은 워크플로 입력
  `marketing_version`으로, 로컬에서는 `bundle exec fastlane beta version:1.2.0`으로
  넘깁니다.
- **빌드 번호**: 워크플로 입력 `build_number`를 준 경우에만 그 값을 쓰고, 아니면
  fastlane이 TestFlight의 최신 빌드 번호에 1을 더합니다.

CI는 `macos-26` 러너와 Xcode 26.6으로 고정합니다. 위의 기준 버전을 올리면 두
워크플로의 `xcode-version`도 함께 올려 주세요. 액션은 메이저 태그(`@v4`, `@v2`)로
고정되어 있으니, 공급망 위험을 더 줄이려면 커밋 SHA로 바꿉니다.

### 개인정보 매니페스트

`App/Resources/PrivacyInfo.xcprivacy`는 필수입니다. 앱이 직접 하는 통신은 iTunes
조회, YouTube(Data API와 내장 플레이어), LRCLIB이고 어느 쪽에도 사용자 식별자를
넘기지 않습니다. **광고 SDK(Google Mobile Ads)는 데이터를 수집합니다.** SDK는 자기
매니페스트를 함께 싣고 Xcode가 합쳐 개인정보 보고서를 만들지만, 앱 매니페스트에도
Google 안내에 따른 항목을 적어 두었습니다 — 기기 ID, 광고 데이터, 제품 상호작용,
충돌·성능·기타 진단 데이터, 대략적 위치(IP 기반). 비맞춤 광고만 요청하고 ATT를
띄우지 않으므로 추적(`NSPrivacyTracking`)은 거짓입니다.

필수 사유 API는 UserDefaults(CA92.1)입니다. `JustSensei`와 `JustDesign`은 동적
프레임워크라 앱 매니페스트가 그 안의 호출을 덮지 못하므로, 각자
`Modules/<모듈>/Resources/PrivacyInfo.xcprivacy`를 갖습니다(ITMS-91053). 다른
모듈에서 UserDefaults 같은 필수 사유 API를 쓰기 시작하면 그 모듈에도 매니페스트를
추가하고 `Project.swift`에서 `hasResources: true`로 연결해야 합니다.

### App Store Connect 개인정보 라벨 체크리스트

라벨은 매니페스트에서 자동으로 채워지지 않습니다. 출시 전, 그리고 SDK를 올릴 때마다
확인합니다.

- [ ] Xcode Organizer에서 아카이브의 **Privacy Report**를 뽑아 SDK 매니페스트까지
      합친 수집 항목을 확인
- [ ] Google의 최신 [AdMob 데이터 공개 안내](https://developers.google.com/admob/ios/privacy/data-disclosure)와 대조
- [ ] 「데이터 수집함」으로 답하고 다음 항목 입력: 기기 ID, 광고 데이터, 제품
      상호작용, 충돌 데이터, 성능 데이터, 기타 진단 데이터, 대략적 위치
- [ ] 용도: 제3자 광고, 분석, 앱 기능 — 항목별로 매니페스트와 같게
- [ ] 「사용자에게 연결됨」·「추적에 사용됨」은 아니오 (비맞춤 광고, ATT 없음) — Google
      안내가 바뀌면 여기와 매니페스트를 함께 고치기
- [ ] 앱 자체는 계정·연락처·사용자 콘텐츠를 수집하지 않음 (가사·단어·복습 기록은 기기에만)
- [ ] 개인정보 처리방침 URL에 광고 SDK와 동의 화면(UMP) 내용 반영

## 테스트

```bash
xcodebuild -workspace Just.xcworkspace -scheme Just \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=latest' test
```

순수 로직만 덮습니다 — 파싱, 스케줄링, 문자열 처리. 지금까지 실제로 나온 버그가
전부 그 영역이었고, 기기·계정·모델 없이 검증할 수 있는 부분도 거기까지입니다.
테스트는 250개가 넘고, 그중 여러 개는 실제로 겪은 회귀를 그대로 고정해 둔 것입니다:
CRLF 가사 분할, 번역본 오선택, 동음이의어 표기 뒤바뀜.
